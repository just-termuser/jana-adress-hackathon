# Jana Extract — извлечение полей адреса без нормализации

Решение для хакатона Jana Post × Terricon Valley. Сервис разбирает строку адреса
на поля и возвращает **ровно то, что написано**: «казибек би» остаётся «казибек би»,
падежи и опечатки не трогаются. Работает полностью офлайн.

> Это самостоятельный проект. Он не связан с SaaS-движком нормализации адресов
> Jana Address Intelligence, который решает обратную задачу.

## Быстрый старт

```bash
docker compose up --build        # http://localhost:8000 — интерфейс, /docs — Swagger
```

Один адрес — `POST /parse` с телом `{id, raw_address}`:

```bash
curl -s -X POST localhost:8000/parse -H "Content-Type: application/json" \
     -d '{"id": "rec_00417", "raw_address": "город Алматы/Алматы қаласы, Мкр Аксай 3а, 59, кв 70"}'
```

```json
{"id": "rec_00417", "raw_address": "город Алматы/Алматы қаласы, Мкр Аксай 3а, 59, кв 70",
 "province": "Алматы", "city": "Алматы", "district": "Ауэзовский", "living_area": null,
 "street_type": "микрорайон", "street_name": "Аксай 3а", "house": "59", "apartment": "70",
 "entrance": null, "floor": null, "landmark": null, "confidence": 0.93}
```

Пакет — `POST /parse/batch` с массивом таких записей:

```bash
curl -X POST localhost:8000/parse/batch -H "Content-Type: application/json" \
     --data-binary @tests/fixtures/sample_input.json
```

Контейнер не ходит в сеть: справочник лежит внутри образа. Проверено запуском с
`--network none`.

### Локально, без Docker

```bash
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
uvicorn jana_extract.api:app --port 8000           # API + интерфейс
python -m jana_extract tests/fixtures/sample_input.json -o out.json   # CLI
pytest                                             # тесты
```

На Windows для корректного вывода кириллицы в консоль: `set PYTHONUTF8=1`.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/parse/batch` | Массив `[{id, raw_address}]` (или `{"records": [...]}`) → массив ответов в том же порядке |
| POST | `/parse` | Одна запись |
| POST | `/parse/file` | Загрузка `.json`, `.jsonl`, `.csv` (`id,raw_address`), `.txt`; `?format=csv` — ответ в CSV |
| GET | `/health` | Проверка живости |
| GET | `/reference/info` | Версия и объём справочника |
| GET | `/` | Веб-интерфейс |

Параметры запроса:
- `?debug=true` — добавить в запись `_meta`: уверенность по полям (`field_confidence`),
  позиции полей в строке (`spans`), нераспознанные токены (`leftovers`), неоднозначности
  с кандидатами (`ambiguity`), официальные названия и коды КАТО (`official`), поля,
  выведенные из справочника (`inferred`, например `{"street_type": {"value": "улица",
  "source": "reference:Алматы", "share": 1.0, "n": 5}}`). Без флага ответ строго по
  схеме из условия.
- `?infer_street_type=false` — не выводить тип улицы из справочника (по умолчанию
  включено; глобально — переменная `JANA_INFER_STREET_TYPE=0`).

**Гарантии:** на каждую входную запись приходит ровно одна выходная запись. Пустая
строка, `null`, число вместо строки или исключение внутри парсера дают запись с
`null`-полями и `confidence: 0`.

## Веб-интерфейс

Можно загрузить файл или вставить адреса построчно. Найденные поля подсвечиваются
цветом прямо в исходной строке. Любую ячейку можно отредактировать: если правка
перестаёт быть подстрокой адреса, ячейка получает красную рамку. Есть фильтр
«только уверенность ниже порога» и экспорт в JSON или CSV. Правки хранятся в браузере.

## Как это устроено

```
raw_address
  └─ tokenizer   токены со смещениями start:end в исходной строке
  └─ parser      шаги, каждый «съедает» свои токены:
       шум (страна, индекс) → номера с маркерами (кв 70, 239 кв, 11дом)
       → адм. единицы с маркерами (г., қаласы, обл., р-н) → город в начале строки
       → улица / мкр / ЖК с маркером → ориентир → адм. единицы по справочнику
       → улица без маркера (Назарбаева8) → дом и квартира по позиции
  └─ resolve     province/district из справочника, выбор street vs living_area
  └─ confidence
```

**Инвариант подстроки обеспечивается по построению.** Текстовое поле — это всегда
`raw[первый_токен.start : последний_токен.end]`. Нормализация (`fold()`: регистр,
ё/е, казахские буквы, ь/ъ) используется только для поиска в справочнике и в ответ
не попадает. Инвариант проверяется тестами на всех фикстурах и фаззингом.

Ключевые решения:

- **Слитное написание.** Буквы и цифры — разные классы символов, поэтому
  `66квартал`, `Назарбаева8`, `11дом`, `кв70` делятся естественно. Литера дома
  (`12а`) и дроби (`1/2`, `33/1`) остаются одним токеном, так что `1/2 ≠ 1`.
  Склейка литеры с маркером (`85адом`) отдельно распознаётся как `85а` + `дом`.
- **Направление маркеров номеров.** Маркер может стоять до числа (`кв 70`) или
  после него (`239 кв`, `5 подьезд`). Привязка выбирается глобально: перебираются
  все варианты, и берётся набор с максимальной суммой очков. Очки дают слитность,
  точка после сокращения и язык маркера: казахские `үй`, `пәтер`, `қабат` обычно
  стоят после числа.
- **рус/қаз через слэш.** «город Актобе/Ақтөбе қаласы»: половина с казахскими
  буквами или маркерами (`қаласы`, `көшесі`, …) помечается как вторичная. Значения
  берутся из русской половины, казахская их подтверждает. Если после казахской
  половины нет запятой («…/Астана қаласы Толе би 19»), она заканчивается на своём
  маркере.
- **Микрорайон: улица или living_area.** Если отдельной улицы нет, микрорайон идёт в
  `street_type`/`street_name`. Если улица есть, микрорайон уходит в `living_area`.
  ЖК всегда идёт в `living_area`. Номер после названия мкр (`Аксай 3а`) включается в
  название, если такой мкр есть в справочнике или дальше есть другой номер под дом.
- **Справочные поля.** `province` — «Актюбинская область» или «Алматы» для городов
  республиканского значения. `district` — без слова «район». `street_type` — полное
  слово («улица», «проспект», «микрорайон»). Если типа в строке нет, `street_type = null`:
  тип не угадывается.
- **district, когда его нет в строке.** Такой район восстанавливается из справочника.
  По ТЗ он не входит в автоматическую метрику и оценивается на защите.
  - Алматы, Астана, Шымкент: район берётся по микрорайону или ЖК, а если их нет — по
    улице. Он выдаётся, только если не меньше 75% адресов с этим названием лежат в одном
    районе (порог выбран по кривой «точность/покрытие», см. `reports/stage2.md`).
  - Райцентры и сёла: берётся район населённого пункта, но только если НП однозначен.
    Это значит, что после учёта области и района из строки остаётся ровно один НП с таким
    названием. Если Алексеевок десять, district = `null`, а уверенность ниже.
  - Города областного значения (вне районов): `null`.
- **Осознанное решение: на улице, которая делится между районами, district = `null`.**
  Неверный район хуже пустого, поэтому для таких улиц мы не угадываем. Это стоит около
  6% покрытия восстановления, зато точность восстановленного района — 0,99.

### Confidence

У каждого поля своя уверенность:
- явный маркер — около 0,95;
- точное совпадение со справочником — около 0,9;
- нечёткое совпадение — около 0,75;
- позиционная догадка — 0,6–0,85.

Итоговое значение — взвешенное среднее по группам с весами жюри: адрес 60%
(city, street_name, house), детали 25%, справочные 15%. Каждый нераспознанный
токен снижает его на 8%. Значение ниже 0,75 — повод проверить запись вручную,
в интерфейсе для этого есть фильтр.

## Справочник

Три производных файла лежат в `data/` и внутри Docker-образа. Исходники в Git не попадают:
PBF лежит в `osm/` в корне репозитория (`kazakhstan-261015.osm.pbf`, Geofabrik), КАТО xlsx —
в `data/raw/`, обе папки в `.gitignore`.

| Файл | Размер | Источник | Что даёт |
|---|---|---|---|
| `reference.json.gz` | 0,75 МБ | OpenStreetMap, выгрузка Geofabrik `kazakhstan-261015.osm.pbf` (2026-10-15) | области, районы, НП, улицы, мкр/ЖК; район улицы/мкр в Алматы, Астане, Шымкенте (point-in-polygon при сборке) |
| `kato.json.gz` | 0,17 МБ | КАТО, Бюро национальной статистики РК: `КАТО_18.09.2026.xlsx`, sha256 `7b87e0a8a72818ca5adcc7b4a7792dd0afd1a3165ed163197012c7c154d4e990`, https://stat.gov.kz/ru/classifiers/statistical/21/ | официальные названия и коды, принадлежность НП району, районы городов областного значения |
| `street_types.json.gz` | 0,47 МБ | OSM: названия дорог и `addr:street`, где тип записан словом | тип улицы, если его нет в строке |

Справочник загружается за 0,5 с.

**Атрибуция.**
- © участники OpenStreetMap, данные под лицензией ODbL.
- КАТО — классификатор Бюро национальной статистики Агентства по стратегическому
  планированию и реформам РК (stat.gov.kz).

**Приоритет источников.**
- **КАТО:** официальные названия и коды областей, районов и НП, принадлежность НП району.
- **OSM:** улицы, микрорайоны, ЖК и всё, что зависит от геометрии (район по улице).
- **Выходной формат** для сущностей, которые есть в OSM, остаётся форматом примера ТЗ:
  «Абайская область», «Байконур». Официальная форма КАТО («область Абай», «район Байқоңыр»)
  отдаётся в `_meta.official`.
- **Переключатели:** `JANA_KATO_CANONICAL=1` выводит формы КАТО везде, `JANA_KATO=off`
  отключает КАТО (остаётся один OSM).

**Покрытие до и после КАТО:**

| | Только OSM | OSM + КАТО |
|---|---|---|
| Области и города респ. значения | 20 | 20 (все сопоставлены с КАТО) |
| Районы | 191 | 197: 189 сопоставлены с КАТО, 6 новых районов городов областного значения — **Актобе** (Алматы, Астана), **Караганда** (им. Казыбек би, Әлихан Бөкейхан), **Тараз** (Жібек жолы, Әулиеата) |
| Населённые пункты | 7 260 | 10 837: у 6 097 из 7 260 НП OSM (84%) есть код КАТО, 3 577 сёл только из КАТО |
| Улицы | 27 544 | 27 544 (OSM) |
| Мкр / ЖМ / ЖК | 6 471 | 6 471 (OSM) |

Подробности:
- **Сёла только из КАТО** (без координат и населения) ищутся при маркере («с.», «ауылы») или
  когда область указана в строке. Без такого контекста они не перехватывают названия улиц.
- **Конфликты источников:** в 68 случаях район НП по КАТО не совпадает с районом по полигону
  OSM, часто это районы реформы 2022 года. Используется КАТО, список — в
  `reports/kato_conflicts.md`.
- **Районы городов областного значения** распознаются, когда написаны в строке. Восстановить
  их по улице нельзя: в КАТО нет геометрии. Если района нет в строке, district = `null`.

**Тип улицы, если его нет в строке.**
- Берётся самый локальный уровень, где название встречается хотя бы 3 раза: город
  республиканского значения → область → страна.
- Тип выдаётся, только если один вариант набирает не меньше 90%. Иначе `null`, а кандидаты с
  долями уходят в `_meta.ambiguity.street_type`.
- `street_name` при этом не меняется.
- Независимая проверка на 5 000 отложенных адресах OSM (в таблицу не входили,
  `tools/eval_street_types.py`): точность 0,998 при покрытии 0,744. Для сравнения, «всегда
  улица» даёт 0,851.

## Что реализовано, что смоделировано, что оставлено на развитие

**Реализовано полностью**
- Извлечение 11 полей без нормализации. Текстовые поля — всегда подстроки исходной строки
  (инвариант проверяется тестами и фаззингом).
- REST API: `/parse`, `/parse/batch`, `/parse/file`. CLI, веб-интерфейс с ручной правкой и
  экспортом. Docker, работа офлайн.
- Справочник из OSM и КАТО с атрибуцией, sha256 источника и отчётом о покрытии.
- Восстановление района: по НП (принадлежность по КАТО) и по мкр/улице в городах
  республиканского значения. Тип улицы из справочника. Выведенные значения помечены в
  `_meta.inferred` и в интерфейсе («из справочника»).
- Честная неоднозначность: одноимённые НП и районы дают кандидатов в `_meta.ambiguity`, без
  молчаливого угадывания.
- Симулятор метрики жюри, синтетический корпус, таксономия ошибок, пороги-трещотки в тестах.

**Смоделировано (без реальных данных организаторов)**
- Точность на скрытом наборе. Эталон организаторов — одна запись. Остальная оценка — на
  собственной ручной разметке (40 записей) и синтетике (2000 записей из названий
  справочника). Синтетика — средство диагностики, а не прогноз.
- Правила метрики: группы 60/25/15, «район учитывается, только если он есть в строке» — по
  тексту ТЗ. Пунктуация при сравнении удаляется, а не заменяется пробелом.
- Точность вывода типа улицы проверена на отложенных адресах OSM, а не на адресах Jana Post.

**Дальнейшее развитие**
- Районы городов областного значения по улице: нужна геометрия районов Караганды, Актобе,
  Тараза, её нет ни в OSM, ни в КАТО.
- Калибровка порогов и confidence на реальном `train.json`: инструменты готовы
  (`tools/diagnose.py --input`).
- Адреса без запятых с несколькими неизвестными словами подряд: «жк Жулдыз 2 Венецианова
  229дом» — где кончается ЖК и начинается улица.
- Выходной формат названий (формат примера ТЗ или официальный КАТО) — после уточнения у жюри.

## Качество и скорость

```bash
python tools/eval.py tests/fixtures/sample_input.json tests/fixtures/sample_output.json
python tools/eval.py --cases tests/fixtures/holdout_cases.json --show-errors
python tools/eval.py --cases tests/fixtures/synth_corpus.json
python tools/diagnose.py --cases tests/fixtures/synth_corpus.json --out reports/diag_synth.md
python tools/bench.py --n 1000 --run
```

`eval.py` — симулятор метрики жюри:
- каждое поле сравнивается посимвольно, после lower case и удаления пунктуации;
- поле, пустое и в эталоне, и у нас, не учитывается;
- веса 60/25/15: область/город/улица/дом, квартира/подъезд/этаж, район/жилой массив;
- район учитывается, только если он есть в строке. Восстановленный район оценивается
  отдельно, по точности и покрытию.

| Набор | Записей | Итог | Природа эталона |
|---|---|---|---|
| `sample_output.json` | 1 | 1.000, все 11 полей | организаторы |
| `holdout_cases.json` | 40 | 0.988 | ручная разметка по ТЗ до первого запуска |
| `synth_corpus.json` | 2000 | 0.998 | синтетика из названий справочника (OSM + КАТО) с «грязными» паттернами ТЗ; средство диагностики, а не прогноз |

Восстановленный район на синтетике: точность 0.990, покрытие 0.936.
Тип улицы из справочника, независимая проверка на отложенных адресах OSM: точность 0.998
при покрытии 0.744 (`python tools/eval_street_types.py`).
Ход работ и цифры до/после — в `reports/stage2.md`, `reports/stage3.md`, `reports/stage4.md`.

Скорость на 1000 записей: около 0,3 с в процессе и через HTTP в контейнере без
сети. Контейнер (220 МБ) готов к работе через 2,5 с, справочник загружается за 0,5 с.

## Известные ограничения

- Эталон организаторов — одна запись. Точность на скрытом наборе оценена по
  собственной разметке и может отличаться, если разметка жюри трактует поля иначе.
  Особенно это касается `street_type` при отсутствии типа, границ `landmark` и
  `living_area`.
- Районы городов областного значения (Караганда, Актобе, Тараз) взяты из КАТО и
  распознаются, только когда написаны в строке. Восстановить их по улице нельзя: в КАТО
  нет геометрии.
- В 68 случаях район НП по КАТО расходится с районом по полигону OSM; используется КАТО
  (`reports/kato_conflicts.md` — для ручной проверки).
- Названия, которые есть в OSM, выводятся в формате примера ТЗ («Абайская область»), а не
  в официальной форме КАТО («область Абай»). Переключатель: `JANA_KATO_CANONICAL=1`.
- Тип улицы, выведенный из справочника, проверен на адресах OSM. Если разметка жюри
  ставит `street_type = null` для незаписанного типа, выключите вывод:
  `?infer_street_type=false`.
- `district` для Алматы, Астаны и Шымкента, когда его нет в строке, выводится по мкр
  или улице, только при доле ≥ 75% адресов в одном районе. Улицы, которые делятся
  между районами, дают `null` (осознанное решение, см. выше).
- Запись «4-12» без маркеров трактуется как дом 4, квартира 12.
- Одноимённые НП и районы («Аксу», «Абайский район»): сначала учитываются область и
  район из строки, затем улики — улица или мкр, которые есть только у одного кандидата.
  Если явный лидер есть (город против одноимённых сёл), он сохраняется. Если кандидаты
  равноправны, province = `null`. В обоих случаях кандидаты видны в
  `_meta.ambiguity` (`?debug=true`).
