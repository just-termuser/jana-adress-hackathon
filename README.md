# Jana Extract — извлечение полей адреса без нормализации

Решение для хакатона Jana Post × Terricon Valley. Сервис разбирает строку адреса
на поля и возвращает **ровно то, что написано**: «казибек би» остаётся «казибек би»,
падежи и опечатки не трогаются. Работает полностью офлайн.

> Это отдельный проект. SaaS-движок Jana Address Intelligence в корне репозитория
> решает обратную задачу (нормализацию) и здесь не используется.

## Быстрый старт

```bash
cd hackathon
docker compose up --build        # http://localhost:8000 — интерфейс, /docs — Swagger
```

Проверка:

```bash
curl -X POST localhost:8000/parse/batch -H "Content-Type: application/json" \
     --data-binary @tests/fixtures/sample_input.json
```

Контейнер не ходит в сеть: справочник лежит внутри образа. Проверено запуском с
`--network none`.

### Локально, без Docker

```bash
cd hackathon
python -m venv .venv && . .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements-dev.txt
uvicorn jana_extract.api:app --port 8000           # API + интерфейс
python -m jana_extract tests/fixtures/sample_input.json -o out.json   # CLI
pytest                                             # тесты
```

На Windows для корректного вывода кириллицы в консоль: `set PYTHONUTF8=1`.

## API

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/parse/batch` | Массив `[{id, raw_address}]` (или `{"records": [...]}`) → массив ответов в том же порядке |
| POST | `/parse` | Одна запись |
| POST | `/parse/file` | Загрузка `.json`, `.jsonl`, `.csv` (`id,raw_address`), `.txt`; `?format=csv` — ответ в CSV |
| GET | `/health` | Проверка живости |
| GET | `/reference/info` | Версия и объём справочника |
| GET | `/` | Веб-интерфейс |

`?debug=true` добавляет в каждую запись `_meta`: уверенность по полям, позиции
полей в строке и нераспознанные токены. Без флага ответ строго по схеме из условия.

**Гарантии:** на каждую входную запись приходит ровно одна выходная запись. Пустая
строка, `null`, число вместо строки или исключение внутри парсера дают запись с
`null`-полями и `confidence: 0`.

## Веб-интерфейс

Можно загрузить файл или вставить адреса построчно. Найденные поля подсвечиваются
цветом прямо в исходной строке. Любую ячейку можно отредактировать: если правка
перестаёт быть подстрокой адреса, ячейка получает красную рамку. Есть фильтр
«только уверенность ниже порога» и экспорт в JSON или CSV. Правки хранятся в браузере.

## Как это устроено

```
raw_address
  └─ tokenizer   токены со смещениями start:end в исходной строке
  └─ parser      шаги, каждый «съедает» свои токены:
       шум (страна, индекс) → номера с маркерами (кв 70, 239 кв, 11дом)
       → адм. единицы с маркерами (г., қаласы, обл., р-н) → город в начале строки
       → улица / мкр / ЖК с маркером → ориентир → адм. единицы по справочнику
       → улица без маркера (Назарбаева8) → дом и квартира по позиции
  └─ resolve     province/district из справочника, выбор street vs living_area
  └─ confidence
```

**Инвариант подстроки обеспечивается по построению.** Текстовое поле — это всегда
`raw[первый_токен.start : последний_токен.end]`. Нормализация (`fold()`: регистр,
ё/е, казахские буквы, ь/ъ) используется только для поиска в справочнике и в ответ
не попадает. Инвариант проверяется тестами на всех фикстурах и фаззингом.

Ключевые решения:

- **Слитное написание.** Буквы и цифры — разные классы символов, поэтому
  `66квартал`, `Назарбаева8`, `11дом`, `кв70` делятся естественно. Литера дома
  (`12а`) и дроби (`1/2`, `33/1`) остаются одним токеном, так что `1/2 ≠ 1`.
  Склейка литеры с маркером (`85адом`) отдельно распознаётся как `85а` + `дом`.
- **Направление маркеров номеров.** Маркер может стоять до числа (`кв 70`) или
  после него (`239 кв`, `5 подьезд`). Привязка выбирается глобально: перебираются
  все варианты, и берётся набор с максимальной суммой очков. Очки дают слитность,
  точка после сокращения и язык маркера: казахские `үй`, `пәтер`, `қабат` обычно
  стоят после числа.
- **рус/қаз через слэш.** «город Актобе/Ақтөбе қаласы»: половина с казахскими
  буквами или маркерами (`қаласы`, `көшесі`, …) помечается как вторичная. Значения
  берутся из русской половины, казахская их подтверждает. Если после казахской
  половины нет запятой («…/Астана қаласы Толе би 19»), она заканчивается на своём
  маркере.
- **Микрорайон: улица или living_area.** Если отдельной улицы нет, микрорайон идёт в
  `street_type`/`street_name`. Если улица есть, микрорайон уходит в `living_area`.
  ЖК всегда идёт в `living_area`. Номер после названия мкр (`Аксай 3а`) включается в
  название, если такой мкр есть в справочнике или дальше есть другой номер под дом.
- **Справочные поля.** `province` — «Актюбинская область» или «Алматы» для городов
  республиканского значения. `district` — без слова «район». `street_type` — полное
  слово («улица», «проспект», «микрорайон»). Если типа в строке нет, `street_type = null`:
  тип не угадывается.
- **district, когда его нет в строке.** Для Алматы, Астаны и Шымкента он выводится по
  улице или микрорайону: берётся район, где больше всего адресов с этим названием, при
  доле не меньше 60%. Для сёл и райцентров берётся район населённого пункта. Для
  городов областного значения district остаётся `null`.

### Confidence

У каждого поля своя уверенность:
- явный маркер — около 0,95;
- точное совпадение со справочником — около 0,9;
- нечёткое совпадение — около 0,75;
- позиционная догадка — 0,6–0,85.

Итоговое значение — взвешенное среднее по группам с весами жюри: адрес 60%
(city, street_name, house), детали 25%, справочные 15%. Каждый нераспознанный
токен снижает его на 8%. Значение ниже 0,75 — повод проверить запись вручную,
в интерфейсе для этого есть фильтр.

## Справочник

`data/reference.json.gz` весит 0,75 МБ и загружается за 0,3 с. Он собран
`tools/build_reference.py` из OSM PBF Казахстана (Geofabrik, 2026-10-15):

| Что | Откуда | Объём |
|---|---|---|
| 17 областей + 3 города респ. значения | `boundary=administrative`, `admin_level=4` | 20 |
| Районы и районы городов | `admin_level=6` | 191 |
| Населённые пункты | `place=city/town/village/hamlet` + `name*`, `alt_name`, `old_name`, варианты из `addr:city` | 7 260 |
| Названия улиц | `highway=*`+`name*`, `addr:street` | 27 544 |
| Микрорайоны, ЖМ, ЖК | `place=suburb/quarter/neighbourhood`, `landuse=residential`, `addr:place/quarter/suburb` | 6 471 |
| Улица/мкр → район для Алматы, Астаны, Шымкента | point-in-polygon при сборке | ≈ 10 200 |

Полигоны используются только при сборке. В рантайм уходят плоские таблицы. Сам
PBF в репозиторий и образ не попадает (`osm/` в `.gitignore`).

Пересборка:

```bash
# локально (нужны osmium и shapely)
pip install -r requirements-build.txt
python tools/build_reference.py --pbf ../osm/kazakhstan-261015.osm.pbf

# или в Docker
docker compose --profile build-reference run --rm build-reference
```

Сборка занимает около 4 минут.

## Качество и скорость

```bash
python tools/eval.py tests/fixtures/sample_input.json tests/fixtures/sample_output.json
python tools/eval.py --edge tests/fixtures/holdout_cases.json --show-errors
python tools/bench.py --n 1000 --run
```

`eval.py` считает метрику так же, как жюри: lower case, без пунктуации,
посимвольное сравнение по каждому полю и взвешенный итог 60/25/15.

| Набор | Записей | Взвешенная точность |
|---|---|---|
| `sample_output.json` (эталон организаторов) | 1 | 1.000 |
| `holdout_cases.json` (разметка по ТЗ до первого запуска) | 40 | 0.987 на первом запуске, 0.994 после исправления |
| `edge_cases.json` (на нём парсер отлаживался) | 40 | 1.000 — это не оценка |

Скорость на 1000 записей: около 0,2 с в процессе и около 0,22 с через HTTP в
контейнере без сети. Контейнер готов к работе через 2 с.

## Известные ограничения

- Эталон организаторов — одна запись. Точность на скрытом наборе оценена по
  собственной разметке и может отличаться, если разметка жюри трактует поля иначе.
  Особенно это касается `street_type` при отсутствии типа, границ `landmark` и
  `living_area`.
- Районы городов областного значения (например, районы Караганды) в OSM не
  размечены и выводятся только из строки.
- `district` для Алматы, Астаны и Шымкента выводится по названию улицы. Длинные
  улицы, проходящие через несколько районов, дают район большинства адресов или
  `null`.
- Запись «4-12» без маркеров трактуется как дом 4, квартира 12.
- Одноимённые сёла без области или района в строке: выбирается самый крупный
  населённый пункт с пониженной уверенностью.
